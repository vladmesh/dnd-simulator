# Ядро симуляции: время, активность, детализация

Брейншторм-гриль 2026-07-04. Вход — три идеи верхнего уровня: (1) кенши-лайк симулятор без сущности игрока, (2) Brain как полная абстракция принятия решений, (3) слои как регулятор детализации. Выход — консенсус-модель, влитая в [VISION.md](../VISION.md), плюс анализ дрейфов кода от неё. Здесь зафиксированы решения с обоснованиями и отброшенными альтернативами.

Связанные брейнштормы: [game-loop-and-master](game-loop-and-master.md), [npc-lifecycle](npc-lifecycle.md), [living-world](living-world.md), [ecs-and-content](ecs-and-content.md), [round-system](round-system.md).

## Решения

### 1. Player-agnosticism: инвариант движка + творческая максима

**Решение:** движок не знает слова «игрок» (PlayerCharacter = Creature + PlayerBrain, никаких isinstance-привилегий); продукт остаётся игрой для игроков, но мир не прогибается: квесты вплетены и уничтожимы самим миром.

**Отброшено:** «симулятор-песочница, игрок опционален» как идентичность продукта — у симуляции без наблюдателя нет потребителя, а игровой цикл уже работает. Осознанно принято: это творческий эксперимент, продаваемость вторична.

### 2. Активность не транзитивна

**Решение:** активных назначают явно — контент (`always_active`), ГМ, игра по триггерам в критичные моменты. Активный NPC, придя в локацию, не активирует жителей; dormant отвечает на взаимодействия пассивно, не просыпаясь.

**Почему:** транзитивная активация — LOD-каскад: наблюдатель порождает наблюдателей, через N тиков активен весь мир. Отброшены «одно кольцо затухания» (дороже, ценность неочевидна) и «транзитивность с глобальным капом» (вытеснение по приоритету сложнее, чем явное назначение).

### 3. Время: 6-секундный раунд как семантическая истина

**Решение:** одна временная линия на весь мир, никто не убегает вперёд. Семантика — «любой активный проверяется каждые 6 секунд»; физически движку разрешено пропускать раунды, когда доказуемо ничего не меняется (страйды — оптимизация, не модель, можно не делать в первой итерации). Активные между точками решений живут в трёх намерениях: **спит / идёт / ждёт**. Каждое действие несёт длительность. Мир turn-gated: игрок стоит — время стоит. Мультиплеер потом — опциональный таймер хода (как в Героях), по таймауту «продолжаю намерение / end_turn».

**Рассмотренные модели:**
- **A. Честный единый раунд** — все активные ходят каждые 6с. Проблема: вечно активный NPC убивает fast-forward («жду до утра» = churn тысяч раундов) и требует дешёвого фильтра, который становится неявной архитектурой.
- **B. Wake-точки / discrete-event simulation** — мир как очередь событий, сцены как плотные отрезки. Семантически чисто, но больше новых понятий сразу.
- **C. Per-creature tick_interval** — polling, худшее из A и B (жжёт вызовы впустую и всё равно пропускает события между тиками).
- **D. Чисто событийная** — риск мёртвого мира, всё равно нужен tick амбиций; вырождается в B.

**Выбрано:** семантика A + механика B как её реализация/оптимизация. CPU-churn приемлем (десятки существ на ифах — копейки), токены — нет. Ключевой инвариант: **LLM никогда не вызывается на 6-секундном пути** — только на границах намерений.

### 4. Контракт мозга: дешёвый гейт + дорогое решение

**Решение:** Brain расщепляется на `gate()` (чистые ифы, «продолжаю намерение?», хоть каждый раунд, для всех типов мозга) и `decide()` (LLM / человек / дерево — только на границах: завершение намерения, прерывание, триггер, ГМ).

**Следствие для игрока:** путешествующий игрок — активен с намерением «иду», гейт проверяет прерывания (встречи!), человек будится вопросом только когда что-то случилось. Убирает dormant-хак travel-as-wait. Симметрия игрок/NPC достигается именно здесь.

**Мультидействие:** боевой ход остаётся PHB (движение + действие + бонус) — экономику действий не трогаем, на ней стоят классовые механики. Множитель LLM-вызовов (3-5/ход) убирается **планом внутри LlmBrain**: первый вызов хода строит план, дальнейшие choose_action выдают шаги плана со сверкой awareness дешёвой проверкой; расхождение = перепланирование. Движок не меняется.

### 5. Прерывания: встроенные + парные триггеры

**Решение:** прерывания намерений — фиксированный встроенный список: телесное (атаковали/ранили), втягивание в сцену (заговорили/напали/энкаунтер, скриптовый или случайный), прибытие, таймер. Декларативные подписки на мировые события живут **на существе**, не на намерении, задаются контентом/ГМ и **парные**: `{on: началась_война, until: закончилась_война}`. Матчинг — при эмиссии событий против индекса условий (стоимость ∝ потоку событий, не существам × раундам). Требует типизированной таксономии событий (payload'ы — стабильный контракт).

**Отброшено:** pull-гейт (каждый гейт лупит query по слоям каждый раунд — O(N) и «что меня волнует» зашито в код); чистый inbox-push (не отвечает, что *будит*; оставлен в роли «что я узнал» — вход для проснувшегося мозга, не механизм пробуждения); декларативные условия на намерениях (выразительность, которая никому не нужна — намерениям хватает встроенных).

**Информационная честность:** механизм всеведущий (прецеденты в коде: kill reputation, XP). Слухи с задержкой — опциональная надстройка потом, не блокер.

**Следствие:** дорога обязана занимать пространство — travel по рёбрам графа локаций, путешественник всегда в конкретной локации, пути пересекаются. Закрывает `travel-action-type` правильным способом.

### 6. Сцены без игрока: LLM остаётся LLM

**Решение:** ненаблюдаемые сцены симулируются честно и дорогим мозгом — история складывается сама («злодей по дороге к герою реально меняется; никто, включая ГМ, не знает, каким дойдёт»). Токены — топливо эмерджентности.

**Экономия — структурная, не выключением:** важность не свойство события, а свойство уровня решения. Границы намерений и переваривание — всегда LLM (единицы вызовов в игровой день); тактика внутри сцены — правила-исполнитель под LLM-командиром (стратегия на входе в сцену) с **reassess-триггерами**, повышающими тактический момент до сюжетного: союзник упал, HP ниже половины, враг сдаётся/бежит, появился поименованный персонаж (→ бэклог `combat-reassess`). LLM-на-каждый-ход остаётся настройкой гранулы для драматических сцен. Плюс `llm-model-tiering`: ненаблюдаемое — на дешёвой модели.

**Отброшено:** даунгрейд мозга до правил в ненаблюдаемых сценах как дефолт (режет эмерджентную историю — принципиальная ставка проекта); нематериализация без игрока (убивает контентные возможности «злодей лично убил капитана при штурме»). Аргумент задержки (невидимая LLM-сцена стопорит видимую через общий раунд) признан валидным, принят как известный риск: на старте игнорируем, лечится иерархией командир/исполнитель.

### 7. Внутреннее я NPC

**Решение:** двухслойное «я». **Структурное ядро** (читают правила/триггеры/магия/ГМ-панель, пишут переваривание/ГМ/контент): отношения (таргет, тип, интенсивность; не путать с репутацией — та про «как социум видит меня»), цели, мировоззрение (живой alignment: переваривание фиксирует поступки, сдвиг применяет правило по накоплению — гистерезис против LLM-драматизации), настроение (enum). **Свободный слой** — лог мыслей, только для LLM. Ядро авторитетно, дневник — комментарий; противоречие между ними — персонаж в противоречии, не баг.

**Цели — одним списком, два сорта:** типизированные (словарь: kill/protect/reach/obtain/flee/serve... — исполнимы RuleBrain, ставятся контентом/ГМ) и свободные строки (ставит себе сам LLM-активный, читает только LLM). Граница типизации проходит по *существу*, а не по полю: типизация нужна тому, чей мозг обязан цель исполнять. Известное ограничение: выключение LLM-гранулы делает свободные цели мёртвым текстом (откат к типизированным + расписанию) — принято.

**Переваривание:** расширение MemorySummarizer — контракт «обнови ядро + перепиши дневник», триггеры: конец сцены/намерения, переполнение, N игровых часов.

**Магия как CRUD** получает конкретные таргеты: Detect Thoughts → read лога и ядра, Charm → временный override отношения, Modify Memory → mutate хроники, Zone of Truth → constraint.

### 8. Гашение активности

**Решение:** приоритет путей — `always_active` из контента (не гаснут; их «простой» — почти бесплатные длинные намерения) > ручка ГМ в обе стороны > until-событие парного триггера (часто результат работы самого пробуждённого: заключил мир → `war_ended` → погас) > самогашение («моя роль сыграна» — штатное действие мозга; вариант «иду домой, там гасну» — дефолт, dormant-на-месте — fallback).

**Отброшено:** автозатухание по таймауту (N произвольно; призраки — не сумевшие закончить задачу — приняты как «забавная бага», но обязаны быть **видимыми**: панель ГМ со списком активных — кто, с какого момента, почему, чего ждёт). Мандат активации в полном виде не строим, берём только `always_active` + хранение причины активации как инфо-поля.

### 9. Лестница детализации

**Решение:** `число → эфемерное существо → персистентный зародыш → именной NPC → активный NPC`. Материализация анонимной массы поселений из чисел (детерминированный seed: облик/имя повторяемы). Первое взаимодействие создаёт зародыш субъектности, **храповик**: с каждой материализацией копится, вниз не крутится. Зародыш ≠ именной NPC (без расписания/целей/структурной памяти). Именные никогда не сворачиваются в числа (dormant почти бесплатен).

**Истина при переходах — событийная запись:** значимые события (смерть, кража, пожар) пишутся в агрегат немедленно через emit_fn-поток (направление зависимостей не ломается: entities не знает, кто слушает); несущественный дрейф (HP, позиции) — сверка при дематериализации. Тот же механизм чинит `lair-death-event`.

**Отброшено:** «агрегат всегда авторитетен» (каждый handler должен знать про агрегаты — связность вверх); «конкретика авторитетна до дематериализации» (текущая сквадная модель; её дефект уже пойман багом `lair-death-event`: рестарт/сейв до дематериализации теряет смерти).

### 10. Classic-инвариант

**Решение:** **механики и структуры всегда Classic, генераторы содержимого могут быть LLM.** Ни одна механика не читает данных, которые умеет писать только LLM; LLM пишет в те же поля, что читают правила. Машина активности/триггеров/целей/лестницы — целиком движок и данные, LLM там нет. Правиловое переваривание (короткая таблица: атаковал → hates, союзник погиб → горе, цель достигнута → completed) — часть ядра: нужно не столько бесплатной версии, сколько **CI** — вся конструкция тестируется детерминированно без токенов.

**Отброшено:** полный паритет механик (таблица правил никогда не догонит LLM по нюансам, тратит время автора); Classic как деградация-не-продукт (рушит бесплатную версию и отлаживаемость).

### 11. Сессии и интерлюдии

**Решение:** игровое время течёт только в сессии (парадокса «злодей копит историю» vs «мир не живёт между сессиями» нет — жизнь мира измеряется игровым временем, а оно turn-gated). Все вышли — мир заморожен на полушаге: намерения, планы, триггеры, лог мыслей обязаны переживать сейв. Единственный легальный скип — **интерлюдия ГМ** («прошло три месяца»): тот же fast-forward по wake-точкам и тикам слоёв. По умолчанию — совсем без LLM (правиловое переваривание); LLM для ключевых NPC на укрупнённых чекпоинтах — настройка (расширение параметров интерлюдии — вне текущего скоупа).

**Отброшено:** оффлайн-симуляция между сессиями (LLM без зрителя, неограниченный дрейф, противоречие вижну; для «живости» не нужна — злодей и так дойдёт, в игровом темпе).

## Вижн-дрейфы: код vs модель (по убыванию тяжести)

1. **Движок знает игрока.** `activation_manager.py` построен на `isinstance(e, PlayerCharacter)` (якорь = игрок по типу); `move_to` player-only; player-status размазан. Нужен якорь-как-свойство.
2. **Машина активности не существует.** В коде: бинарный флаг «рядом с игроком» + `wake_at_seconds`. Нет намерений, гейта, триггеров, гашения, назначенных активных. Travel — wait-хак с телепортом (дорожные встречи невозможны физически).
3. **Идея 3 реализована на треть.** Двойное представление — только сквады/логова. Поселения — числа без индивидов, материализации/храповика/событийной записи нет; дефект текущей сверки-при-дематериализации уже пойман (`lair-death-event`).
4. **Внутреннее я наполовину пустое.** Целей нет, alignment — мёртвое поле, суммаризатор только сжимает recent (не пишет ядро), правилового переваривания нет — Classic-персонаж не меняется от пережитого.
5. **Экономика LLM.** Мозг дёргается 3-5 раз за боевой ход; нет плана, нет командир/исполнитель.
6. **Сериализация — предусловие.** Уже BLOCKER (кольцо теряет модификаторы, `player-xp-not-persisted`); каждая новая сущность модели умножит боль рукописного формата. «Заморозка на полушаге» работает только при lossless-сейве.
7. **VISION.md разошёлся** — исправлено этим брейнштормом (переписан 2026-07-04).

## Архитектурные ходы

- **Якорь как свойство/capability**, не тип. Дешёвый первый шаг, можно делать сразу.
- **Намерение как первоклассная сущность** на Creature (тип, таргет, прогресс, wake-условия). Съедает wait-хак; travel — по рёбрам.
- **Триггер-таблица** `{on, until}` с матчингом при эмиссии. Предусловие — типизированные payload'ы событий: **спринт 020 фаза 2 копает ровно этот фундамент**.
- **Brain: gate/decide** в контракте; план хода и командир/исполнитель — внутренности LlmBrain, интерфейс движка не меняется.
- **NpcMemory → внутреннее я**: goals, типизированные отношения, живой alignment; контракт суммаризатора «обнови ядро + перепиши дневник»; правиловый близнец.
- **Поселения на двойное представление** по образцу сквадов + событийная запись вверх (заодно `lair-death-event`) + промоушен-храповик.
- **Квесты не строить отдельным движком**: квест ≈ типизированные цели + парные триггеры + награды-события. `quest-system` планировать после триггеров и целей.

**Не трогать (уже правильное):** стек слоёв и направление зависимостей, Brain-стратегия с переключаемыми гранулами, событийная пропагация, контент-как-данные, canned dialogue по (role, activity, mood), сквадная материализация как прототип лестницы.

## Порядок работ (набросок)

После закрытия спринта 020: сериализация-схема → якорь-как-свойство + намерения/travel → триггеры + переработка активации → внутреннее я + переваривание (LLM + правиловый близнец) → лестница детализации для поселений → квесты (к этому моменту — почти чистый контент). `control-interfaces` — ортогонален, порядок относительно него решается при планировании спринтов.
