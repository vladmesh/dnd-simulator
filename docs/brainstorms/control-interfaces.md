# Брейншторм: Управляющие интерфейсы (worldbuilder / DM / админка)

Обсуждение 2026-06-28. Кандидат на отдельный спринт.

Терминология: здесь «DM» (Dungeon Master, человек-ведущий) это не то же, что
«Мастер» из [game-loop-and-master.md](game-loop-and-master.md). Там «Мастер» это
LLM-стратегия ввода-вывода для игрока (аналог Brain). Здесь речь про три
**человеческих** управляющих интерфейса. Чтобы не путать, ведущего-человека
зову DM.

## Три интерфейса, которые хочется

1. **Worldbuilder** — каждый может собрать мир и потом в него играть.
2. **DM** — один человек ведёт кампанию для других: готовит приключения,
   подсовывает их игрокам, наблюдает за столом, варьирует состояние мира в
   некоторых пределах.
3. **Админка (для меня)** — read-only обзор «кто во что играет» плюс
   техническая глубина. Похоже на DM, но без влияния на фикцию и с системным
   срезом.

## Главная интуиция: одно ядро, три проекции

Это не три приложения. Сейчас в коде весь управляющий функционал свален под
один префикс `/api/master/*` **без авторизации**: и CRUD контента, и hot-controls
над живой сессией, и снапшот мира. Это буквально объединение всех трёх
интерфейсов, только без перегородок. Задача не «написать три штуки», а провести
границы внутри уже существующего ядра и спроецировать его тремя линзами.

Линза = роль + область видимости. Ядро (content_loader + GameService) одно.

## Две оси, по которым интерфейсы расходятся

**Ось A — над чем работаешь.** Эта граница в коде уже есть и чистая:

- *Контент* (дизайн-тайм): YAML на диске, `content_loader/`. Схемы, CRUD,
  library / manifest / fork. Состояние между сессиями.
- *Живая сессия* (ран-тайм): in-memory мир в `GameService._sessions`,
  hot-controls, стрим событий.
- *Парк сессий + система*: кросс-сессионный и технический срез. В коде сейчас
  почти не выражен.

**Ось B — полномочия:** писать в контент / читать + нудж в пределах / читать всё
включая техинфо.

Сетка:

|                  | Контент (диск)        | Живая сессия (память)         | Парк + система       |
|------------------|-----------------------|-------------------------------|----------------------|
| **Worldbuilder** | основной дом          | —                             | —                    |
| **DM**           | готовит приключение   | наблюдает + нудж в пределах   | —                    |
| **Админка**      | read для диагностики  | наблюдает read-only + техинфо | основной дом         |

## Структура вложенности — отсюда видно переиспользование

**По authoring: Worldbuilder ⊆ DM.** DM это worldbuilder плюс инстанцирование
плюс запуск. Та же машинка авторинга, просто DM ещё жмёт «запустить» и садится
наблюдать. Отдельный редактор для DM строить не надо.

**По live: Админка ≈ DM минус нудж плюс техника.** На чтении живой сессии они
пересекаются почти полностью. DM сверху добавляет «писать в фикцию»
(hot-controls), админка вместо этого добавляет кросс-сессионную ширину и
внутренние состояния (combat sides, initiative, wake_at, NPC memory, LLM-трейсы).

Переиспользование почти полное по построению. Чисто-новых экранов мало.

## Что переиспользуется конкретно (уже в коде)

Бэкенд, общий для worldbuilder и DM (authoring):

- `content_loader/schemas.py` — Pydantic-схемы всех сущностей, single source of truth.
- `content_loader/schema_gen.py` — JSON Schema для форм + `x-ref-type` для дропдаунов.
- `content_loader/crud.py` — generic CRUD по `EntityType` (layer-сущности и каталоги).
- `content_loader/assembly.py` — `assemble_world`, `create_empty_world`,
  `fork_layer`, `fork_world`, `scaffold_layer`.
- `content_loader/library.py` — каталог шаблонов слоёв + `list_compatible_templates`.
- Роуты: `routes_content.py` (CRUD + `/schemas`), `routes_world.py` (assemble/fork/library).

Бэкенд, общий для DM и админки (live):

- `service/session.py` — `GameSession` + listener-паттерн.
- `service/game_service.py` — реестр сессий + hot-controls.
- hot-controls: `commands_creatures.py` (spawn/patch/delete/brain),
  `commands_time.py` (advance), `commands_world_state.py` (снапшот),
  nation/settlement-патчи в `routes_session.py`.
- `storage/store.py` — save/load (per-world JSON).

Фронт-примитивы:

- Authoring: `master/SchemaForm.tsx`, `master/EntityListEditor.tsx`,
  `master/RefSelect.tsx`, `master/CatalogPicker.tsx`, `master/WorldEditor.tsx`.
- Live-observation: `master/WorldOverview.tsx`, `master/CreatureList.tsx`,
  `master/CreatureForm.tsx`, `master/TimeControl.tsx`, `master/SavesPanel.tsx`,
  `game/BattleMap.tsx`, `game/EventLog.tsx`, `game/LocationPanel.tsx`,
  `game/Perception.tsx`.
- Экраны-каркасы: `MasterScreen` (`/master`), `SessionView` (`/master/:sessionId`,
  уже 4 таба World/Creatures/Time/Saves).

См. также [frontend-architecture.md](frontend-architecture.md) про стор и WS-машину.

## Где реально проходит граница и чего не хватает

Граница идёт не между тремя кодовыми базами, а по роли/области поверх общего
ядра. Не хватает одного камня в основании, без которого три интерфейса даже не
формулируются.

### 1. Identity / ownership / роли — keystone, которого нет вообще

Весь контент глобальный, файловый, ничей. На сессию один `PlayerBrain`.
`/api/master/*` без auth. Без понятия «кто» нельзя сказать ни «каждый создаёт
*свой* мир», ни «*один* ведёт для *других*», ни «кто что играет». Это то место,
где граница начинает что-то значить. Делать первым.

Открытый вопрос: где хранить владение мирами. Сейчас пути контента
(`content/worlds/{id}`) плоские и без пользователя. Варианты: namespace в пути,
отдельный индекс владения, или переход с файлов на БД.

### 2. DM «в пределах» = политика поверх hot-controls, а не новые ручки

Spawn / HP / brain / time / nations / settlements уже реализованы как
безграничный god-mode. DM-интерфейс это те же ручки, обёрнутые лимитами и
кураторской рамкой. Новый код тут тонкий (policy-слой), не новая механика.

### 3. Spectator listener — дешёвый примитив, разблокирующий двоих сразу

Сейчас слушатели событий привязаны к `PlayerBrain` / WS игрока. Смотреть сессию,
не будучи игроком, нельзя. Read-only подписка на события сессии нужна и DM
(наблюдать стол), и админке (наблюдать парк), и зрителям-игрокам. Извлекается раз,
используется трижды.

### 4. Мультиплеер — самый тяжёлый общий фундамент, нужен DM по определению

«Один ведёт для других» это N игроков + приватность awareness (`perceive()` есть,
но раздачи по игрокам нет) + DM как наблюдатель через тот же spectator-канал.
Разблокирует мультиплеерную игру вообще, не только DM. Архитектурно самое тяжёлое.

### 5. «Приключение» — единица, пересекающая границу дизайн-тайм ↔ ран-тайм

То, что DM подсовывает, это бандл контента (encounter-таблицы, lair, loot, NPC).
Он и авторится на диске, и инъектится в живую сессию через spawn. Это один объект
в двух режимах, а не два разных контента. Спринт 018 (lairs/encounters/loot)
делает ровно этот payload.

## Сведение к одной фразе

Контент-слой и сервис-слой это общий двигатель. Три интерфейса это три набора прав
и областей над ним. Разделитель, которого не хватает и который делает остальное
выразимым, это модель идентичности/ролей. Самый дешёвый разблокиратор наблюдения
это spectator-listener.

## Куда копать в спринте

Порядок по зависимостям:

1. Минимальная модель identity / ownership / role, и через неё проекция трёх линз.
   Решить, что делать с уже существующим безавторизационным `/api/master/*`
   (разрезать на роли).
2. Spectator-listener (read-only подписка на сессию).
3. Мультиплеер (N PlayerBrain + приватность awareness) — отдельный тяжёлый блок,
   возможно в свой спринт.
4. DM policy-слой поверх hot-controls + «приключение как бандл».
