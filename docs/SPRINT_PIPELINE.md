# Sprint Pipeline

Процесс разработки одного спринта. Каждый спринт = набор связанных механик, реализованных от планирования до аудита.

## Фазы

### 1. Планирование

- Выбираем механики для реализации.
- Проверяем бэклог на блокеры. Если есть — закрываем блокеры первыми.
- Результат: список механик с обоснованием выбора.

### 2. Архитектура

- Как механики встраиваются в существующую систему.
- Как они будут масштабироваться (не overengineering, но продуманные точки расширения).
- В каком порядке реализовывать (dependency graph).
- Результат: план в `docs/sprints/NNN-name/sprint.md`.

### 3. Разбивка на задачи

- Задачи группируются по фазам. Каждая фаза — понятный небольшой инкремент.
- Фаза = 2-4 задачи, после которых система в рабочем состоянии.
- Результат: чеклист задач в sprint.md с тегами (engine/content/quality).

### 4. Реализация (цикл по фазам)

Для каждой фазы:

1. Реализация задач фазы.
2. `make check` — lint + typecheck + unit tests.
3. **E2E тесты** (Playwright) — smoke path без LLM-мозгов (экономим токены OpenRouter). Сразу ловим баги на стыке фронт↔бэк и фиксим.
4. Коммит.

### 5. Аудит и рефакторинг

- После выполнения всех задач — полный аудит (`/audit`).
- Рефакторинг может занять больше времени чем реализация — это нормально.
- Цель: задел под масштабирование, не копить техдолг.
- Всё что за скоупом или не фиксится быстро → бэклог.

### 6. Финализация

- `/update-docs` — синхронизация документации с кодом.
- Обновление sprint.md: все задачи отмечены, итоги записаны.

## Техспринты

Раз в 4-5 спринтов — техспринт:

- Разбор бэклога целиком.
- Детальный аудит (не только текущий спринт).
- Переписываем/улучшаем skills и документацию.
- Пересматриваем этот пайплайн.

## E2E: правила

- Без LLM-мозгов (`ai: llm` заменяется на `ai: rule` или мок).
- Smoke path: загрузка мира → бой → действие → результат.
- Запускаются после каждой фазы, не только в конце спринта.
- Хрупкие тесты чинятся сразу, не откладываются.

## Бэклог

Всё что не входит в текущий скоуп:

- Идеи возникшие по ходу реализации.
- Баги не касающиеся скоупа напрямую.
- Техдолг найденный на аудите но не критичный.

Записывается в `docs/BACKLOG.md` с приоритетом и тегами.
